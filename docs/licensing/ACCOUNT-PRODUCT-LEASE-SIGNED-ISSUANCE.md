# Agent account-product JWS issuance — preproduction-only trust plan

**Certification intent:** complete the existing authenticated Agent LEASE challenge → live account entitlement/registered machine key → Ed25519 JWS signing → atomic ISSUED audit in one Serializable transaction. Public Agent-only adapters remain disabled by default and unconditionally unavailable in production. This is distinct from the existing commercial license-key protocol, which requires no Google login.

## Invariants

- Only Digital Solutions issues account-product JWS; use the pinned immutable @bke/licensing 0.10.0 Ed25519 provider and v1 claims schema. Do not recreate or rewrite the library.
- Authentication via existing Agent session bearer, never caller-asserted accountId/userId/sessionId. A fresh one-use LEASE challenge and real Ed25519/ES256 possession signature must bind action/product/account/machine and be consumed inside the same database transaction as issuance.
- Live catalog `ACCOUNT` or `EITHER`, active paid/trial rights and registration row locked before signing. `LICENSE_KEY` rejects account JWS while commercial signed lease issuance remains Google-free.
- Dedicated SQL-owned key registry: key ID, ACTIVE / VERIFY_ONLY / REVOKED state and public PEM only; signing private PEM is supplied by a separate server-secret map, never persisted, logged or returned. Exactly one ACTIVE row, verify private/public key pair and kid. Rotation retains old VERIFY_ONLY keys for outstanding leases.
- Both signed output and AGENT_PRODUCT_LEASE_ISSUED audit created inside the same bounded Serializable transaction. Return JWS only after commit. A failure in verification, signing, ISSUED audit or commit returns no JWS. No signing key, bearer, raw JWS, original challenge/signature or PEM is included in audit.
- Expose two narrow Agent-only endpoints only in disposable/preproduction: begin LEASE challenge then issue signed JWS. Unconditionally 404 in production, default-off configuration, distributed per-IP and per-bearer rate limits, bounded strict JSON, no browser Origin and exact Agent protocol version.
- No DS production signing cutover, DB mutation, live provider traffic, Agent/Launcher installer acceptance, npm publication, catalog activation or production deploy. Agent installed trust-anchor verification remains a separate certification intent.

## Implemented source boundaries (PR #362)

- `apps/web/agent-sessions/account-product-lease-issuance.ts`: one non-retried `db.$transaction(..., { isolationLevel: 'Serializable' })` verifies actual LEASE challenge signature (ENROLL refused), burns the nonce, rechecks live account entitlement, product account activation permission, session+machine registration, signs through immutable `@bke/licensing` and writes `AGENT_PRODUCT_LEASE_ISSUED` before commit. Signed bytes are never returned if any step/commit fails; all denied outcomes fail closed.
- `apps/web/agent-sessions/account-product-lease-signer.ts`: separate SQL registry with exact one ACTIVE signing key under `FOR SHARE` lock, PEM material from `ACCOUNT_PRODUCT_LEASE_SIGNING_KEYS_JSON`, independently derives/compares public Ed25519 key and checks versioned JWS contract. No fallback to commercial license signing keys. Rotation is an internal trusted-only transaction: STAGED becomes ACTIVE, prior ACTIVE becomes VERIFY_ONLY, terminal REVOKED cannot be reactivated. No unauthenticated rotation endpoint.
- `prisma/migrations/20261112103000_account_product_lease_signer_registry/migration.sql`: additive SQL-only table with `kid`, public PEM, `keyset:<kid>` reference, state, timestamps, one ACTIVE partial unique index and revocation/identity triggers. **No private keys or production seeded keys**; absent signer fails closed.
- `app/api/agent-sessions/leases/challenge/route.ts` and `/leases/issue/route.ts`: Agent-only POST, BKE protocol header, Authorization bearer (not cookies), reject browser Origin, strict 8KiB request, per-IP and hashed-bearer rate limiting. The body may select product/action/platform/architecture but **cannot assert account/session/user/key identity**. The existing Agent key proof service binds the challenge to all authenticated dimensions.
- `platform/host/config/environment.ts`: `ACCOUNT_PRODUCT_LEASE_ISSUANCE_ENABLED=false` by default, requires independent Agent session/key HTTP flag and a dedicated keyset secret, rejects production enablement; route hard denies production before environment parse. Environment names are generation-independent.
- `tests/agent-session-account-product-lease-issuance.test.ts`, `tests/agent-session-account-product-lease-signer.test.ts`, `tests/agent-session-account-product-lease-http.test.ts`: transactional audit/commit failure, proof/eligibility denial, signer mismatch/multiple/revoked, real JWS verification, rotation safety, no browser-origin/cookie or production exposure.
- `tests/integration/account-product-lease-signing-registry.test.ts`: **real disposable PostgreSQL**, checks single active key, public-only custody, signing, rotation preserving VERIFY_ONLY, and terminal revocation. Core owns database run after migration; Licensing owns hermetic request/signature attack tests. The existing real Agent nonce+entitlement integration is reused, not fabricated in a release.

## Preproduction setup and key custody

Nothing starts automatically. A trusted operator must provision a dedicated Ed25519 key (distinct from commercial signing), insert its **public** PEM and key ID into the SQL-owned registry with status `ACTIVE` and activatedAt, then provide the private PEM through the protected `ACCOUNT_PRODUCT_LEASE_SIGNING_KEYS_JSON` server secret map keyed by `kid`. An example shape is `{ "<approved-kid>": "<encrypted-at-rest-secret-provider-PKCS8-PEM>" }`; never commit this value or store it in the database. Key rotation stages an additional public key and secret map entry before the internal audited rotation transaction. After rotation, previous key stays VERIFY_ONLY for outstanding leases; the Agent must receive a separately certified trusted public keyring for verification.

Enabled ONLY in explicitly configured disposable/preproduction `DEPLOYMENT_ENV`, with `AGENT_ACCOUNT_SESSION_ENABLED=true`, `AGENT_KEY_HTTP_ENABLED=true`, and `ACCOUNT_PRODUCT_LEASE_ISSUANCE_ENABLED=true`. Production must continue returning 404 and has **no** signing cutover, keys or route activation. Even with preproduction signing enabled, this does not prove installed Agent/Launcher acceptance or real TPM attestation.

### Exact-head DB-proof discovery and correction

GitHub Actions reusable Core workflow executes the **main-branch workflow definition** while checking out the pinned candidate source SHA. A new test step authored only on the PR branch is therefore not executed in that generation. The first successful candidate's Core runtime suite reported the new signer-registry PostgreSQL integration as skipped; **that proof was not accepted** despite the green overall workflow. The integration is now selected directly by the existing Core full-runtime test command only when `GITHUB_ACTIONS=true`, `NODE_ENV=test` and the parsed PostgreSQL URL is exactly `localhost:5432/bke_test`. This forbids running against production, private VPS or a developer-local DB, and skips the PR-only job without a database. The extra proposed CI step has been removed to prevent duplicate execution. Only a fresh CI run with **4 passed signer-registry PostgreSQL tests, not skipped**, can complete this certification intent.
